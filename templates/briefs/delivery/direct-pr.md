## Deliver as one pull request

1. Bring the branch up to date with the base: `git fetch origin`; if `git merge-base --is-ancestor origin/{{base}} HEAD` fails, merge `origin/{{base}}` with a merge commit (`git merge origin/{{base}}`, never a rebase), resolve any conflict, re-run what the conflicts touched, and push (under a Disclosure section, not before step 3's review passes).
   A conflict whose resolution is a judgment call on behaviour goes to `coordinator` as `{{task}} QUESTION <the conflict> | options: ...`.
2. Find what your branch made false: for each file, command, flag, setting and path it adds, renames or removes (`git diff --stat origin/{{base}}...HEAD`), `git grep` its name in the repository's Markdown, `CLAUDE.md`, `AGENTS.md` and script headers, and fix every line that no longer holds, in the same PR.
3. Under a Disclosure section in a public repository, push nothing yet: send `{{task}} DONE review-ready <the full sha of HEAD>` to `coordinator`, then wait, since the reviewer reads your local head and the team reviews its wording before anything goes public.
   Fix each finding the coordinator sends you on the branch, pushing nothing; once they are fixed, or the coordinator says the review passed, go on with the push, the checks and the PR.
4. Run the project's local checks ({{local_checks}}) on the head you push with `{{team_bin}}/team-checks {{project}} <full sha>`, which runs them as `team-merge` does, in a fresh detached worktree of that head; fix the branch and push again until all pass on one head.
   They set no GitHub status: their result goes in the PR body.
5. Open one PR from `{{branch}}` to `{{base}}`: `gh pr create --repo {{repo}} --base {{base}} --head {{branch}}`, titled as a Conventional Commit, its body opening with what this PR changes, in words a reader of the repository can follow, with no task, ticket, phase or retro number (the task's goal is "{{goal}}": on a phase, say this phase's part of it alone and name the others as their own PRs), then a line naming the local checks that passed and the head they passed on.
6. Start the wait for the PR's GitHub checks with `{{team_bin}}/team-ci-wait --no-agent-review <full url> <the full sha you pushed>`, run with Bash `run_in_background`, then send `{{task}} PR <full url>` to `coordinator` at once, so the review reads while CI runs, and keep the wait going.
   `--no-agent-review` leaves out the reviewer's `agent-review` status, which may land before your wait's last look: never fix or push for it, since its findings come back to you from the coordinator as a fix round.
   Act on how it ended: exit 0, every check passed or the head has none; exit 1, fix each `the PR's:` failure it names on the branch and push the fix as step 7 says, and never a `roll-up:` line, whose shard's line names the failure; rerun each `infrastructure:` line's check once with the command its line gives and run this wait again on the same head, and when that wait names the same check as infrastructure again, send `{{task}} BLOCKED <the line>` to `coordinator`; or, on a head other than the one you pushed, do as its message says; exit 75, run it again, or report as its message says.
7. Push each fix of a `the PR's:` failure at once, as you pushed the first head: repeat step 1, run step 4 on the new head, bring the PR body's local checks line up to date (`gh pr edit <full url> --body-file <file>`), and start step 6's wait on the new head, but send no new `PR`: the review in flight counts that failure as a `blocking` finding, and its findings come back to you as a fix round, where you note that one as fixed at the head you pushed.
8. Once the wait on the head you last pushed ends with exit 0, the delivery is done: send nothing more, since a review's findings come back to you from the coordinator as a fix round.

Never run a command that needs `sudo`; send `{{task}} BLOCKED <the command> needs sudo` to `coordinator` instead.
